# ADR 0008 — Tags

Status: **Implemented in R6** (repository format 4). Proposed by the
implementer under the owner's delegation; the owner may revise it before
0.1.0, like every format decision of the alpha.

## Context

Releases need stable names ("v1.2.0") for snapshots, and the Git ecosystem
expects them as `refs/tags/<name>`. Until R6 concurv had only branches,
which move. ADR 0007 kept tags on the roadmap (refinement 8, backlog
P2-1).

## Decision

1. **A tag is a shared, named reference to a snapshot that does not move.**
   It lives in the operation view next to branches, in its own namespace
   (`View.tags`), like Git's `refs/tags/` beside `refs/heads/`. Tags are
   *lightweight*: a name and a snapshot, no message, tagger or signature
   (annotated and signed tags are future work; signatures are R7).

2. **Commands.**
   - `concurv tag create <name> [--at <branch|tag|snapshot>]`: at this
     workspace's head by default (else the head of its branch). A name that
     exists is refused; there is no `--force` and no move.
   - `concurv tag list`: tags, sorted by name, with their snapshots.
   - `concurv tag delete <name>`: removes the name only. The snapshot stays
     (objects are never deleted), the operation log keeps the old target,
     and the output prints it, so `tag create <name> --at <id>` restores
     the tag.
   - `undo` refuses `tag-create` and `tag-delete`: tags are shared, and
     others may already rely on them (the rule for `branch-create`).
   - `--at` resolves a branch name, then a tag name, then a snapshot id
     prefix. A string naming a branch and a tag at different snapshots is
     refused as ambiguous (exit 51). `branch create --at` accepts tags too.

3. **Names.** Exactly the rules for new branch names (ADR 0007 §5): Git's
   ref-name rules, the portability policy (ASCII, no Windows-reserved
   characters or device names, at most 200 bytes, not `HEAD`/`@`, reserved
   first components `refs`, `remote`, `remotes`), and no collision with
   another *tag* ignoring ASCII case or as a `/` prefix (Git stores
   `refs/tags/` as files too). A tag may share its name with a branch, as in
   Git; `--at` then refuses to guess (rule 2).

4. **Format.** Tags travel in a second view extension (RFC 0001 §3.4, tag
   byte 2, after the remotes extension, present only when a tag exists), so
   operations without tags keep their exact bytes and ids. A repository
   whose operations may carry it is **format 4**. The first `tag create`
   upgrades the repository from format 1, 2 or 3 to 4 under the repository
   lock, before writing the operation that introduces the tag; builds
   before R6 refuse a format-4 repository with `CONCURV_UNSUPPORTED_FORMAT`
   (exit 12) instead of misreading it.

5. **Reachability.** Tag targets are roots for `verify` (and for any
   future garbage collection), like branch heads.

6. **Git bridge** (ADR 0002).
   - `concurv git export --tags` also writes every tag whose snapshot is in
     the exported history as a lightweight `refs/tags/<name>`, together
     with the branch, in one `git update-ref --stdin` transaction: a tag
     missing in Git is created, an equal one is left alone, and a tag that
     exists in Git with another target refuses the whole export
     (`CONCURV_DIVERGED`, no Git reference changes). Tags outside the
     exported history are listed, not exported.
   - `concurv git import --tags` creates a concurv tag for each Git tag
     (lightweight, or annotated and peeled to its commit) whose commit is
     in the imported history, in the same operation that publishes the
     branch. Annotated tags lose their message and tagger (the output
     counts them). Tags outside the history and names concurv refuses are
     skipped and listed. A concurv tag of the same name at the same
     snapshot is kept; at another snapshot, the import is refused
     (`CONCURV_DIVERGED`) before anything changes.

7. **Sync.** Relays do not exchange tags yet (RFC 0003 protocol version 1
   has no tag messages). Across machines, tags travel through Git export
   and import, or are created on each machine. A relay-side tag set with
   create-only compare-and-swap is the planned extension.

## Consequences

- Release names are stable references that `verify` protects and Git
  understands.
- Format 4 is one more one-way upgrade, triggered only by using the
  feature; repositories that never tag stay readable by older builds.
- Tags are local plus Git for now; a team using only relays must create
  them on each machine until relay tags exist.
